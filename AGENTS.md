# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## What this is

Modulate is a browser extension (WXT + Preact) that transposes YouTube video audio by semitones (±12) **and** time-stretches playback speed (0.5×–2×, pitch held constant), per video. State persists in `chrome.storage.local` keyed by YouTube video ID. UI is a popup (live controls) plus an options page (master switch + saved-video management). Keyboard `commands` and a toolbar badge are driven by the background script. See `ROADMAP.md` for planned work (in-player controls, `sync` storage).

## Commands

Package manager is **bun** (`bun.lock`).

- `bun run dev` — dev server, Chrome (MV3) at `.output/chrome-mv3-dev`
- `bun run dev:firefox` — dev server, Firefox (MV2)
- `bun run build` / `bun run build:firefox` — production build
- `bun run zip` / `bun run zip:firefox` — packaged extension for store upload
- `bun run compile` — `tsc --noEmit` type check
- `bun run lint` / `bun run lint:fix` — oxlint (`.oxlintrc.json`); whole repo minus `ignorePatterns`, with the typescript + unicorn + oxc + import + react + jsx-a11y plugins (vitest only under the test override)
- `bun run format` / `bun run format:check` — oxfmt (`.oxfmtrc.json`): tabs, no semi, single quote, trailing commas, import sort
- `postinstall` runs `wxt prepare` (regenerates `.wxt/` types); run it manually if imports/types look stale

Tests run via Vitest (`bun run test` / `test:watch`; `test:coverage` adds a V8 coverage report, HTML in `coverage/`) — happy-dom env (`*.test.ts`/`*.test.tsx`): unit specs for `lib/`, Testing Library specs for the popup and options pages, entrypoint specs for the content, injected and background scripts (each realm on its own, messages driven by hand), an audio-engine spec against a hand-rolled fake Web Audio graph, and an offline spec (`lib/stretchNode.test.ts`, node environment) that runs the **real** Signalsmith processor — WASM included — quantum by quantum through `lib/testing/stretchSim.ts`: pitch across the transpose × tempo grid, latency, dropouts, and the port protocol `lib/stretchNode.ts` speaks. None of them run a real audio graph, a real render deadline or the real three-realm message flow, so also verify changes by loading the unpacked build and exercising the popup (and the options page) on a YouTube watch page — in Firefox too for anything touching the content/page channel.

CI: `.github/workflows/check.yml` runs compile, lint, format check, tests and both builds on every push to `main` and every PR; `release.yml` repeats the checks before submitting a tagged release.

## Architecture: three realms, two message hops

The core constraint driving the whole design: the Web Audio graph **must run in the page's MAIN world**, not the content-script sandbox. Firefox throws `DataCloneError` when an `AudioWorkletNode` serializes a sandbox-created object into the page-realm worklet. So responsibilities are split across three realms (popup→content and content⇄injected are the two hops; the background script is a side actor for shortcuts + badge):

```
popup (Preact) --PopupMessage-->  content script  --ApplyMessage (JSON string)-->   injected (MAIN world)
                browser.tabs       |   ^          <--StatusMessage (JSON string)--
                .sendMessage       |   |       CustomEvents on the injected <script>
                                   |   | PopupMessage (keyboard commands) /
                                   |   | BadgeMessage (effective state + status;
                                   v   |               an open popup listens too)
                              background (commands + toolbar badge)
```

- **`entrypoints/popup/`** — Preact UI. A thin remote: sends `PopupMessage` to the active tab's content script and renders the returned `PlayerState` (pitch + tempo steppers/sliders, global + per-video toggles, reset). Owns no logic. Renders an empty state when the tab has no content script (not YouTube, or a YouTube tab opened before an install/update — then it asks for a reload; `activeTab` is what makes the tab URL readable for that) or is not on a watch page. Shows the page engine's `AudioStatus` when it isn't simply playing (waiting for a click in the page, no player, failure), and a failed write as an error rather than a state. The status stays live while the popup is open: it listens for its tab's `BadgeMessage`s, because a change's reply leaves before the page has applied it; `audioSeq` decides whether a reply or a push is newer. Has a button to open the options page.
- **`entrypoints/options/`** — Preact UI. Edits storage **directly** (not via messages): the global switch and the list of saved per-video settings — recently tuned first, a search box past six entries, a per-row on/off toggle, remove one, and clear all (behind an inline confirm). Shared UI pieces (`Toggle`) live in the root `components/`, outside `entrypoints/`, where WXT would read a folder as an entrypoint. Content scripts re-apply live via storage watchers, and the page itself watches the same keys (`watchVideoSettings` for the per-video ones) so it stays in sync with edits made from the popup.
- **`entrypoints/content.ts`** — runs on `*://*.youtube.com/*`. **Owns storage.** Injects `injected.js` into the page via a `<script src=…>` tag (not inline — YouTube CSP blocks inline; that is also why it isn't WXT's `injectScript`, which inlines the text on MV2) and keeps that element as the private channel to it. Resolves which video the tab is on — the one the URL names (`/watch?v=`, `/shorts/`, `/live/`; `getVideoId`), or, over a page that names none, the miniplayer's while `ytd-app[miniplayer-is-active]` is set (the page reports it in a `PlayingMessage`; the player keeps a closed miniplayer's id, hence the attribute check) — then its effective pitch/tempo from storage + toggles (`resolveSetting`), forwards them to the main world, and posts a `BadgeMessage` to the background (again whenever the page engine reports a new `AudioStatus`). Re-applies on SPA nav (`yt-navigate-finish` event + WXT's `wxt:locationchange` as the fallback: Navigation API where available, a 1s URL poll otherwise), on storage changes to the global switch or **its own video's** entry, on a back/forward-cache restore (`pageshow` with `persisted`: the script didn't restart, and nothing fired while the page was frozen), on the miniplayer opening or closing (a `MutationObserver` on that attribute), and when the miniplayer moves on to another video (it autoplays without a navigation). Every storage mutation runs through one `serialize()` chain — per-video writes are read-modify-write of a single record, so concurrent handlers lose updates. On context invalidation (extension disabled/updated/uninstalled) it posts a no-op, because the page-realm engine outlives it. It still sends a `processorUrl` (resolved with `browser.runtime.getURL`) for 1.4-era page scripts that require it; the current page script ignores it.
- **`entrypoints/injected.ts`** — runs in MAIN world. Owns the Web Audio graph (`lib/audioEngine.ts`). Listens for `APPLY_EVENT`s on the `<script>` element that loaded it (read from `document.currentScript` at startup), finds the `<video>` (the one in `#shorts-player` on a Shorts page, `#movie_player` otherwise, which also plays the miniplayer; with a `MutationObserver` since it mounts late), builds the graph, applies pitch + tempo, and posts a `StatusMessage` back after each apply settles. It also reports which video `#movie_player` holds (`getVideoData()`, MAIN world only) as a `PlayingMessage`, whenever that changes (capturing `loadstart`/`loadeddata`/`playing` on the document) and to each channel it adopts. Behaviors worth knowing before editing it: **the latest message always wins** — every trigger (new message, media-event replay, first-gesture retry) only marks the latest `ApplyMessage` dirty for a single worker, and `apply()` bails after each await when a newer one arrived, so a reset can never be overtaken by an older change still waiting on a gesture, the `<video>` or the build; it **lazily captures** (only a transpose builds a graph: tempo alone is `attach`ed and played natively, and a no-op with a bound element is undone in place without re-resolving the element); while a transpose waits for a gesture, its tempo already plays natively; it **replays** on the element's `loadstart`/`emptied`/`ratechange`, rebinding those listeners when YouTube swaps the `<video>`, because the nav event fires before the media is ready; a **second copy stands down** (Firefox re-injects content scripts on update, and only the first instance can own the captured element) after handing its channel to the first instance through the function stored under `Symbol.for('modulate.injected')`, which listens and reports on every channel it has adopted; and it disposes the context on `pagehide` **only when not entering bfcache** (see invariants below).
- **`entrypoints/background.ts`** — drives keyboard `commands` (forwards `NUDGE_*` `PopupMessage`s, marked `fromShortcut`, to the active tab; the content script then shows a brief on-page notice via `lib/toast.ts`, and changes nothing while the video or extension is switched off) and renders the per-tab toolbar badge, **icon** and tooltip (both values spelled out, plus why they aren't playing) from `BadgeMessage`s sent by content scripts (muted tint while the page waits for a click, `!` on an engine failure): colored icon on a watchable video, grayscale otherwise (the grayscale set is generated by `modules/generate-disabled-icons.ts` and is the manifest's `default_icon`). It also resets the icon on full-document navigation, since a per-tab override would otherwise strand the colored icon after leaving YouTube, and on every start runs `migrateLegacyStorage` (idempotent) to move pre-1.4 installs off the single-object layout and drop the old engine's quality knobs.

### Message protocol (`lib/messaging.ts`)

`lib/messaging.ts` is imported by the MAIN-world bundle, so it must stay free of extension APIs (it pulls only the side-effect-free `lib/settings.ts` and `lib/youtube.ts`; `lib/stretchNode.ts`, the other MAIN-world module, is likewise free of extension APIs).

`PopupMessage` (popup/background→content): `GET_STATE | SET_SEMITONES | NUDGE_SEMITONES | SET_TEMPO | NUDGE_TEMPO | SET_VIDEO_ENABLED | SET_GLOBAL_ENABLED | RESET`. Content always replies — with a `PopupResponse`: `{ ok: true, state: PlayerState }` (`videoId`, `globalEnabled`, `enabled`, `semitones`, `tempo`, `audio`) or `{ ok: false, error }`. A failure is never answered with a default-valued state, which would read as a reset.

`BadgeMessage` (content→extension: the background, and an open popup): the effective `semitones` + `tempo` for the sending tab, `onVideo` (whether the tab is on a watchable video), the engine's `status`, and `audioSeq`, which increments with every status change in the tab (`PlayerState` carries it too, so the popup can order a reply against a push). The background renders/clears the badge text — pitch as a bare number, tempo-only as `♪`, `!` on an engine error — tints it by status, and picks the colored or grayscale icon from `onVideo`.

The content/page hop runs over the injected `<script>` element: `APPLY_EVENT` / `STATUS_EVENT` CustomEvents dispatched on it, never `window.postMessage`, which every script in the page can read and forge. Both payloads cross the content/page membrane as the event's `detail`, so they are **JSON strings** — a raw object arrives as `null` in the page realm (Firefox without `cloneInto`, Chrome's isolated worlds).

`ApplyMessage` (content→injected). Carries the resolved `semitones` and `tempo` — **not** the worklet URL: the page script resolves that beside its own `<script src>` (and refuses to start unless that is a `chrome-extension://`/`moz-extension://` URL), because it goes straight to `audioWorklet.addModule` and anything in the MAIN world can post on the channel. Always `JSON.stringify` on send. On receive, `parseApplyMessage` validates **every** field, not just the discriminant, and clamps the numbers onto the storage ranges: the channel narrows who can reach the listener, but the MAIN world is shared with YouTube's own scripts and any other extension injecting there, and an out-of-range number reaches restricted-float writes that throw. A payload carrying our marker that fails validation logs a warning.

`StatusMessage` (injected→content, JSON string too): the `AudioStatus` of the latest apply — `idle | applied | waiting-for-gesture | no-video | error`. A forged one is acceptable because it only changes what the popup and badge say.

`PlayingMessage` (injected→content, JSON string, on `PLAYING_EVENT`): the `videoId` and `title` the main player holds. Used only while the miniplayer is open over a page whose URL names no video. `parsePlayingMessage` holds the id to `isVideoId` (`[A-Za-z0-9_-]`, it becomes a storage key); a forged one can only pick which of the viewer's own saved settings the miniplayer gets, or where a change made there is saved.

Routine "nobody is listening" messaging failures go through `logSendFailure` (debug level); anything else warns.

`GET_STATE` is a pure read fired on popup mount and **must never touch the audio graph** — otherwise the popup response blocks on graph build / context resume. Only mutating messages call `apply()` (fire-and-forget).

## Audio engine invariants (`lib/audioEngine.ts`)

These are load-bearing; violating them mutes audio or throws:

- `createMediaElementSource` may be called **only once per element, for the document's lifetime** — not once per context. A second call throws `InvalidStateError` even from a fresh context, and closing the old context does not release the element (closing makes its output _ignored_, it does not restore direct output). After it runs, the element no longer outputs to speakers directly — all audio flows through the graph. So "off" = bypass the worklet (route source straight to `destination`, tempo back to the element's native handling), and the real rule is that **every path through `route()` must end with the source reaching `destination`** — leaving it disconnected mutes the video with no recovery short of a reload.
- **One context and one worklet serve the page for its lifetime.** YouTube keeps one `<video>` across SPA navigations (only the pitch/tempo parameters change), but swaps it for ads/miniplayer and may swap an earlier one back. Each element is captured once into that same context (`sources`, a `WeakMap` from element to source node): the current one takes the worklet path, and the element being left is rewired **straight to `destination`**, since it can play no other way now and may come back — switching back reuses its source. The context is closed only on real unload (`dispose`) or when it never captured anything (a failed open: autoplay refusal, worklet load, or a first capture that throws); closing one mutes every element it captured for good, and an element captured into a closed context is refused up front (it can't be captured again). `ensureGraph` is idempotent and safe to await concurrently — including for _different_ elements, where it waits out the in-flight build rather than handing back a promise that would resolve against the wrong `<video>`. A build never touches the element's rate before capture (a native tempo keeps playing through it), and capturing a new element into an existing context first checks the context still runs, like the first build.
- `route()` falls back to the bypass wiring on a throw and records the no-op to match it. A worklet `processorerror` also routes around the worklet, and the graph stays bypassed until a new element gets a fresh worklet node in the same context (if that one fails to load too, it stays bypassed).
- Tempo is always the **element's** `playbackRate`, in one of two modes. **Without a transpose** (and with a crashed worklet) it is the browser's native time-stretch: `preservesPitch = true`, the graph bypassed or never built — no capture, no gesture, nothing of ours to fail. **With a transpose** the element resamples raw (`preservesPitch = false`, pitch drops like a record) and the worklet's shift undoes it in the same pass as the transpose (`stretchSemitones` = `semitones − 12·log2(tempo)`; in live-input mode Signalsmith ignores any rate) — one stretch, not two; with `preservesPitch` left on, the compensation would double-correct. **At tempo 1** the engine hands the rate back to the page (`preservesPitch = true`, and it resets `playbackRate` only if it was the one driving it); otherwise a pitch-only setting would make YouTube's own speed menu resample raw and shift pitch uncorrected. `attach(el)` binds the rate element without a graph, handing a previous one back to the page.
- The worklet trails its input by ~145 ms (its reported latency, checked by `lib/stretchNode.test.ts`) and the video is not delayed to match; the context adds its own output latency on top (logged at debug level after each build).
- An inactive Signalsmith worklet outputs silence, so `route()` activates it exactly while it is in the path (`setActive`), including on the fallback after a throw.
- An `AudioContext` only runs once the browser's autoplay policy allows it — after a gesture in the page, or earlier for sites the browser trusts (Chrome's media engagement score, which regular YouTube viewers clear; a Firefox per-site autoplay permission). Capturing into a context that never starts plays the element silently, so `build()` **starts the context and checks it is `running` before capturing**; otherwise it closes it and throws `AudioBlockedError`, having captured nothing. Don't replace this with a `navigator.userActivation` check — that over-blocks the trusted-site case. On `AudioBlockedError`, `injected.ts` marks itself blocked (so it doesn't open a probe context on every trigger, each of which Chrome logs) and retries on the first `pointerdown`/`keydown` in the page itself: popup clicks and shortcuts happen in another browsing context and grant the YouTube document nothing. A context the browser suspends **after** the build (`statechange`, via `onStateChange`, registered only once the build's own start is done) re-runs the latest apply in `injected.ts`, which reports `waiting-for-gesture` and arms the retry, or `applied` once it runs again. `resume()` is bounded by a timeout (generous for the pre-capture check, so a slow start isn't misread as a refusal): on a context that isn't allowed to start it stays pending (per spec), and an unbounded await would stall the apply worker.

## Storage (`lib/storage.ts`) and setting rules (`lib/settings.ts`)

WXT storage: `local:globalEnabled` (master switch) and one `local:video:<videoId>` key per tuned video (a `VideoSetting`: `{ enabled, semitones, tempo, title?, updatedAt? }`; `updatedAt` is stamped only when pitch or tempo changes, so the options list can sort by last tuned). Only `globalEnabled` is exported raw; the rest is private behind accessors (`getRawVideoSetting`/`setVideoSetting`/`listVideoSettings`/`watchVideoSettings`/…). One key per video, not one shared object, because every write to a shared object is a read-modify-write of every entry, and `serialize()` only orders writes within one tab — two tabs (or the options page and a tab) writing at once would drop one. Pre-1.4 installs have the single `local:videoSettings` object and the old engine's `local:audioQuality` knobs; `migrateLegacyStorage` (run by the background on every start) moves the former (an entry already under its own key wins) and deletes both.

The value rules live in `lib/settings.ts`, side-effect-free so every realm can import them: ranges, clamps, `DEFAULT_VIDEO_SETTING`, `NO_OP`, `isNoOp` (the single no-op check — storage pruning, engine bypass, lazy capture and the badge all call it) and `resolveSetting(global, video)`, the single source of truth for what gets applied: the no-op (`{ semitones: 0, tempo: 1 }`) when the global switch is off, no per-video entry exists, or that entry is disabled; otherwise the entry's values.

Ranges are enforced by `normalize()` on **every read and every write** — never at call sites. `normalize()` builds entries field by field, so unknown keys and a non-string `title` are dropped, and a stored value that isn't an object reads as no entry. Storage types are unchecked assertions (`defineItem`'s `fallback` only fires when the key is absent), so a value written by an older version or edited from devtools arrives typed as a `VideoSetting` without having been one, and an out-of-range `tempo` reaches `element.playbackRate`: `0` freezes the video, `NaN` throws mid-reroute and mutes it. Clamp ranges: `MIN/MAX_SEMITONES` (±12) and `MIN/MAX_TEMPO` (0.5×–2×, snapped to `TEMPO_STEP`). Writes prune: an **enabled** entry sitting at the no-op is deleted rather than stored, because `resolveSetting` cannot tell it from having no entry — it would only clutter the options list and a future `sync` quota. This makes `RESET` self-cleaning. A **disabled** entry is kept even at the no-op: "off for this video" is a real choice that has to survive to be listed and toggled back on. Growth is therefore bounded by videos actually tuned, not by videos visited.

## The stretch worklet — Signalsmith Stretch (`lib/stretchNode.ts`)

Transposing runs through [Signalsmith Stretch](https://signalsmith-audio.co.uk/code/stretch/) (`signalsmith-stretch`, MIT): a phase-vocoder pitch shifter compiled to WASM, in an AudioWorklet. It replaced SoundTouch's WSOLA, which needed three fixes of our own against crackling and still measured ~22–25 dB less clean on tones and chords and doubled transients when shifting up (the comparison lives on the `spike/signalsmith` branch).

- **No package factory.** Its main-thread factory bundles the whole WASM build (114 KB) into whatever imports it — here the MAIN-world script — and loads the worklet from a Blob URL, which YouTube's CSP refuses. The worklet file self-registers wherever it is evaluated as a worklet module, so `modules/signalsmith-processor.ts` copies it to `signalsmith-processor.js` (web-accessible, loaded from the extension URL) and `lib/stretchNode.ts` speaks its port protocol directly: `[id, method, ...args]` out, `[id, result]` back, `['ready', …]` once the WASM has instantiated. WASM compiles inside the worklet; YouTube's CSP allows it (`'unsafe-eval'`). Startup (`ready` plus the first `configure`/`latency` calls) is bounded by `START_TIMEOUT_MS` and fails on `processorerror`: a worklet that never starts would otherwise hang the build and, behind it, `injected.ts`'s apply worker.
- **Pinned to 1.3.2** (exact version in `package.json`): on a channel-count change its processor calls a bare `configure()` that throws, so the node is pinned to explicit stereo. Re-check that before bumping.
- **Config (`STRETCH_CONFIG`):** 120 ms blocks, 30 ms interval, `splitComputation`. A longer block resolves close partials (chords) better at the cost of delay (90 ms: ~35 ms less delay, ~8 dB less clean on a triad). Splitting spreads each block's FFT work over the quanta in between — ~30 ms more delay, but the worst quantum costs ~5× less, and per-quantum spikes are what miss Firefox's worklet deadline.
- **Limiter.** Re-synthesis changes phase relationships between partials: loudness holds, but peaks can rise (~2× on a sawtooth). A `DynamicsCompressorNode` just under full scale (ratio 20, 2 ms attack) catches them, followed by `LIMITER_TRIM`, which cancels the compressor's automatic makeup gain so the processed path plays exactly as loud as the bypass (checked in Chromium: 0.00 dB).

Why a web-accessible file and not a Vite `?url` import: WXT inlines `?url` assets as a `data:` URI, and the worklet loads in YouTube's MAIN world where the page CSP would govern (and can block) a `data:` module. A `chrome-extension://` web-accessible file sidesteps that. New web-accessible resources for the page must be registered in `wxt.config.ts` under `web_accessible_resources`.
